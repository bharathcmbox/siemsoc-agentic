Who is this? Connecting the dots across logs

A security platform takes in logs from dozens of systems: an endpoint sensor on each laptop, the firewall, DNS, DHCP, the sign-in service, the people directory. Each one names the same laptop and the same person in its own way. Every alert, risk score and investigation depends on working out which records describe the same thing. Get it wrong, and one laptop under attack looks like three quiet ones.

Design rules behind this pipeline

Step 1 · Fingerprint: what kind of text is this?

The platform tries each format it knows, and picks the one that splits every line the same way.

Step 2 · Propose: three clues for each field

Name
Does the field name look like names other sources use for this meaning? (src_ip, client, cip …)
Shape
Do the values look like this kind of value: an address, a domain, a time, an account?
Seen before
Do the values match things you already hold? This is the strongest clue: if every value is a laptop name you already know, the field holds laptop names, whatever it is called.

Things to get right

Keep the original text.Store every raw line, and keep fields you couldn't map under their original names. A wrong guess can be fixed later; a field you threw away can't.
Direction matters as much as type.Knowing a and b are both addresses isn't enough. Mix up which one is the source and every connection points the wrong way.
Mapping when stored vs when searched.If meanings are applied when logs are stored, a fix only helps new logs. If they are applied when you search, a fix applies to old logs too, at the cost of slower searches.
An AI assistant can draft the mapping. A person approves it.AI can propose a parser from sample lines and a plain description. It reads text that outsiders can write, though, so treat the log text as data, never as instructions. See when the logs talk back.

Patterns you'll find in real platforms

Different products package these ideas differently, but the building blocks are the same.

One shared set of field names

Every source is mapped onto one common schema, so a rule written once works on all of them. Fields that don't fit are kept, not dropped.

The sensor as the best bridge

A first-party endpoint sensor knows its own name, addresses, hardware address and signed-in user in real time. Third-party logs that only carry an address are tied to a device through it.

Links with a time range

A context graph stores each link with when it was true, and looks back a few days so late-arriving logs still get linked.

Ranked sources of truth

When the asset inventory, the directory and the sensor disagree, a ranked list decides which one wins for each field.

Lookups when you search

Some platforms attach names to events when you search, from lookup tables. A correction to a table applies to all history at once.

Context added when stored

Others add names to events as they are stored, which makes searches fast. Corrections then need a backfill, or an alias table that every search goes through.

AI-drafted parsers

An assistant drafts the mapping for an unknown format from sample lines. A person reviews it before it is switched on.

Deny lists for shared values

Shared addresses, proxies, service accounts and placeholder names like "localhost" are kept out of matching, so they can't chain thousands of entities into one.
